## 1. 任务类型

### 1.1 按职业分类

| 任务类型 | 适用职业 | 匹配度基准 |
|----------|----------|------------|
| 设计任务 | 设计师 | 90-100% |
| 编码任务 | 程序员 | 90-100% |
| 测试任务 | 测试员 | 90-100% |
| 分析任务 | 分析师 | 90-100% |

### 1.2 按规模 / 难度分类

| 类型 | 难度 | 基础积分 | 基础 XP | 完成时间 |
|------|------|----------|---------|----------|
| 简单任务 | ★ | 10-15 | 20 | 1-3 秒 |
| 普通任务 | ★★ | 20-30 | 50 | 5-10 秒 |
| 困难任务 | ★★★ | 40-50 | 100 | 15-30 秒 |
| 史诗任务 | ★★★★ | 80-100 | 200 | 60+ 秒 |

### 1.3 按性质分类

| 类型 | 说明 | 可协作 |
|------|------|--------|
| 个人任务 / 单人任务 | 单 Agent 独立完成，只需 1 人 | 否 |
| 协作任务 | 需要多个 Agent 配合，`is_collaborative=True` | 是 |
| 子任务 | 从主任务拆分 | 否 |
| 灵感任务 | 交流中产生的新想法 | 可能 |
| **竞争任务**（v2.0 新增） | 同职业≥2 空闲 Agent 举手时触发抽签 | 有竞争 |

### 1.4 任务分类总表（v2.0）

| 类型 | 触发条件 | 分配方式 | 竞争 |
|------|----------|----------|------|
| **单人任务** | 普通任务，只需 1 人 | 城主指派 / 自动分配 | 无 |
| **协作任务** | `is_collaborative=True`，需多人 | 城主指派多人 | 无 |
| **竞争任务** | 同职业≥2 空闲 Agent 举手 | 抽签决定 | 有 |

## 2. 任务生成与分配

### 2.1 任务生成

#### 2.1.1 自动生成

| 来源 | 频率 | 说明 |
|------|------|------|
| 系统生成 | 每日 | 自动生成当日待办任务 |
| 协作触发 | 不定期 | Agent 交流产生新任务 |
| 挑战触发 | 周期性 | 大挑战拆分出的任务 |

#### 2.1.2 生成规则

- 每日 8:00 自动生成当日任务（3-5 个）
- 任务池上限：10 个待领取任务
- 超过上限时不再自动生成

#### 2.1.3 任务池结构

```
任务池 (TaskPool)
├── pending[]      // 待领取
├── inProgress[]   // 进行中
├── completed[]    // 已完成
└── failed[]      // 已失败
```

### 2.2 任务分配流程

#### 2.2.1 原始分配流程（v1.0）

```
主 agent 选择任务 → 主 agent 选择 Agent → 系统判断匹配度 → 分配 / 拒绝
```

#### 2.2.2 分配评分算法（v2.0）

单人任务分配时，使用综合评分选择最优 Agent：

```python
def score_agent(agent: Agent, task: Task) -> float:
    # 基础分：能量充足给高分
    energy_score = agent.energy / 100

    # 专注度：working 时扣分
    focus_score = agent.focus / 100 if agent.status == "idle" else 0.5

    # 职业匹配：完全匹配给 1.0，无关给 0.3
    profession_score = 1.0 if agent.profession == task.required_profession else 0.3

    # 关系值加成（≤ 10%）
    relation_bonus = min(agent.relation / 1000, 0.1)

    return energy_score * 0.3 + focus_score * 0.2 + profession_score * 0.4 + relation_bonus
```

#### 2.2.3 匹配度判定（v1.0）

| 匹配度 | 分配结果 | 效果 |
|--------|----------|------|
| ≥ 60% | 允许分配 | 正常效率 |
| 20-59% | 允许分配 | 效率下降，匹配度持续下降 |
| < 20% | 拒绝分配 | 提示主 agent 重新选择 |

#### 2.2.4 分配限制

- 每个 Agent 同时最多持有 2 个任务
- 同一任务不能分配给多个 Agent（协作任务除外）
- 休息室中的 Agent 不能分配任务

## 3. 单人任务流程

### 3.1 流程

```
[任务发布]
    ↓
[检测职业匹配 Agent]
    ↓ 有匹配？
    ├─ 有 → 指派给最优 Agent（关系值 / 能量 / 专注度综合评分）
    └─ 无 → 提示城主：无可用 Agent
    ↓
[任务开始] → Agent 状态变为 working
    ↓
[任务进行中] → 城主可查看进度
    ↓
[任务完成] → 结算奖励 + 更新 Agent 状态
```

### 3.2 执行状态

| 状态 | 说明 | 可中断 |
|------|------|--------|
| pending | 待开始 | 是 |
| in_progress / working | 执行中 | 是 |
| paused | 暂停 | - |
| completed | 已完成 | - |
| failed | 失败 | - |

### 3.3 执行消耗

| 消耗项 | 数值 | 说明 |
|--------|------|------|
| 饱食度 | -0.5/秒 | 工作消耗 |
| Token 配额 | -10/次 | 通信消耗（不是 / 秒） |
| 社交需求 | +0.3/秒 | 工作时孤独感累积 |

### 3.4 进度计算

```
进度 += 基础速度 × 匹配度修正 × 情绪修正 × 技能加成
```

| 修正项 | 公式 |
|--------|------|
| 匹配度修正 | 匹配度 < 60% 时 = 匹配度 / 60 |
| 情绪修正 | 兴奋 +20%, 积极 +10%, 低落 -10%, 焦躁 -20% |
| 技能加成 | 效率型技能每级 +10% |

### 3.5 完成判定与汇报

- 进度达到 100% 时任务完成
- **层层汇报流程**：
  1. 先向干系 Agent 交流（相关参与任务的 Agent）
  2. 再向上级 Agent 汇报
  3. 逐级汇报至主 agent
- **无法跳过汇报流程**

### 3.6 城主决策：Agent 可拒绝任务

- 能量 < 20% 时可拒绝任务
- 拒绝后扣关系值 -5
- 避免滥用拒绝机制

## 4. 协作任务（含状态机）

### 4.1 概述

协作是多个 Agent 配合完成任务的机制，需要主 agent 协调或由 Agent 自主触发。

### 4.2 触发条件

- 多个相关 Agent 同时接受同一任务
- 由主 agent 主动发起协作
- 或 Agent 自主交流触发

### 4.3 协作加成

| 加成条件 | 效果 |
|----------|------|
| 双 Agent 协作 | 效率 +30%，总 Token 消耗 -20% |
| 关系度 ≥ 80% | 额外效率 +15% |
| 职业互补 | 额外质量 +20% |

### 4.4 协作任务职业质量加成（v2.0）

| 组合 | 质量加成 |
|------|----------|
| 程序 × 设计 | +20% |
| 程序 × 测试 | +15% |
| 设计 × 产品 | +15% |
| 三职业协作 | +30% |

### 4.5 城主决策

- 协作任务最小人数：**2 人起**（鼓励小规模协作）
- 协作任务超时：扣除 **50% 奖励**

### 4.6 协作流程

```
[协作任务发布]
    ↓
[城主指派 N 名 Agent]（职业互补有额外质量加成）
    ↓
[子任务拆分] → 自动按人数拆分子任务
    ↓
[并行执行] → 各 Agent 独立执行子任务
    ↓
[汇总验收] → 所有子任务完成 → 触发协作奖励结算
    ↓
[奖励发放] → 基础奖励 × 协作加成 × 关系值系数
```

### 4.7 协作状态机

#### 4.7.1 状态定义

| 状态 | 说明 | 入口条件 |
|------|------|----------|
| idle | 无协作 | 默认状态 |
| collab_requested | 协作请求中 | 主 agent 发起或 Agent 自主请求 |
| collab_pending | 等待确认 | 协作请求发送，等待响应 |
| collab_active | 协作进行中 | 所有参与者确认 |
| collab_holding | 协作暂停 | 等待资源或决策 |
| collab_completed | 协作完成 | 任务完成，触发结算 |
| collab_failed | 协作失败 | 协作中断或失败 |

#### 4.7.2 状态转换图

```
                    ┌─────────────────────────────────────────┐
                    │                                         │
                    ▼                                         │
┌─────────┐    ┌────────────────┐    ┌─────────────────┐      │

    │           ┌──────────────────────────────┘               │

         └──────────────┘        (取消)
             │
             │ 确认
             ▼
    ┌─────────────────┐

       ┌─────┴─────┐
       │           │
   正常完成     中断/暂停
       │           │
```

#### 4.7.3 详细状态说明

##### idle（空闲状态）

```yaml
状态: idle
说明: 默认状态，无协作进行

进入条件:
  - 游戏开始
  - 协作完成
  - 协作失败/取消

退出条件:
  - 主 agent 根据 AI 推理结果发起协作请求

可执行动作:
  - 主 agent 发起协作请求
  - 自由移动
```

##### collab_requested（协作请求中）

```yaml
状态: collab_requested
说明: 协作请求已发起，等待参与者确认

进入条件:
  - 主 agent 根据 AI 推理发起协作请求

退出条件:
  - 所有 Agent 确认 → collab_pending
  - 任意 Agent 拒绝 → idle
  - 超时 (5 秒) → idle

数据记录:
  - 主 Agent: 发起者
  - 辅助 Agent[]: 被邀请者
  - 任务 ID: 关联任务
  - 请求时间: 发起时间戳
```

##### collab_pending（等待确认）

```yaml
状态: collab_pending
说明: 等待各 Agent 确认是否参与协作

进入条件:
  - collab_requested 中所有 Agent 未拒绝

退出条件:
  - 所有 Agent 确认 → collab_active
  - 任意 Agent 拒绝 → idle
  - 超时 (3 秒) → idle

每个 Agent 的确认状态:
  - pending: 待确认
  - accepted: 已接受
  - rejected: 已拒绝

确认检查:
  - Agent 当前状态是否可以参与协作
  - Agent 是否愿意参与（基于关系值）
  - Agent 是否满足协作要求
```

##### collab_active（协作进行中）

```yaml
状态: collab_active
说明: 协作任务正式执行

进入条件:
  - collab_pending 中所有 Agent 确认

退出条件:
  - 任务完成 → collab_completed
  - 被中断 → collab_holding
  - 失败 → collab_failed

进行中效果:
  - 效率 +30%（双 Agent）
  - 关系度 ≥ 80% 时额外 +15%
  - 职业互补时质量 +20%
  - Token 消耗 -20%
  - 头顶气泡显示 3 秒协作对话

进度计算:
  进度 += (基础速度 × 效率加成) / 参与人数
```

##### collab_holding（协作暂停）

```yaml
状态: collab_holding
说明: 协作因某种原因暂停

进入条件:
  - 协作中任意 Agent 被中断
  - 等待主 agent 决策
  - 资源不足

暂停原因:
  - Agent 电量耗尽
  - 主 agent 叫停
  - 需要决策

退出条件:
  - 问题解决 → collab_active
  - 超时 (10 秒) → collab_failed
  - 主 agent 取消 → idle

处理选项:
  1. 等待恢复
  2. 更换参与者
  3. 取消协作
```

##### collab_completed（协作完成）

```yaml
状态: collab_completed
说明: 协作任务成功完成

进入条件:
  - 协作任务进度达到 100%

结算内容:
  - 积分奖励: +50（基础）+ 效率加成
  - XP 奖励: 正常 XP × 1.5
  - 城主 XP: +25
  - 情绪值: +15（每个参与者）
  - 关系值: +3（参与者之间）
  - 可能触发灵感创意（额外奖励）

后续动作:
  - 自动进入汇报流程（层层汇报：先干系 Agent 交流 → 逐级向上汇报 → 至主 agent）
  - 触发庆功系统（可选）
  - 触发复盘系统
  - 返回 idle 状态
```

##### collab_failed（协作失败）

```yaml
状态: collab_failed
说明: 协作任务失败

进入条件:
  - collab_holding 超时
  - 任务无法完成
  - 主 agent 主动取消

失败后果:
  - 任务进度清零或保留 50%
  - 参与者情绪 -10
  - 关系值 -2
  - 可能影响后续协作意愿

后续动作:
  - 提示主 agent 原因
  - 可选择重新协作
  - 返回 idle 状态
```

## 5. 竞争机制

### 5.1 模块概述

任务竞争模块用于解决"同职业多个 Agent 空闲时，任务分配给谁"的问题。触发后通过纯随机抽签决定任务归属。

| 属性 | 值 |
|------|-----|
| 模块名称 | 任务竞争 |
| 英文名 | TaskCompetition |
| 触发场景 | 同职业 ≥ 2 个 Agent 空闲，同一任务只能分配给 1 人 |
| 分配方式 | 纯随机抽签（不举手、不先到先得） |
| 影响范围 | 情绪值、关系值、任务执行 |

### 5.2 触发条件

| 条件 | 说明 | 技术描述 |
|------|------|---------|
| 任务人数 | 只需要 1 人 | `task.required_agents == 1` 或 `task.is_collaborative == False` |
| 空闲人数 | 同职业 ≥ 2 名空闲 Agent | `agent.status == 'idle'` 且 `agent.current_task is None`，从 `agents.profession` 字段读取 |
| 举手数量 | 多个 Agent 同时举手 | Agent 自动检测任务要求并举手 |

**三者同时满足时，触发竞争抽签流程。**

### 5.3 竞争方式：纯随机抽签

```
竞争方式：纯公平抽签（无加权）
```

- 所有举手 Agent 拥有**等概率**中签机会
- 不考虑关系值、职业等级、历史完成任务数
- 城主**不可干预**，只能旁观
- 生产环境使用 `secrets.randbelow`（密码学安全随机）
- 调试模式可通过环境变量 `COMPETITION_DEBUG=true` + `COMPETITION_DEBUG_SEED=42` 切换为固定种子

#### 抽签算法

```python
# 生产环境
import secrets
winner = candidates[secrets.randbelow(len(candidates))]
```

### 5.6 加倍惩罚

> **版本冲突说明**：关于"加倍惩罚"的触发条件，多版文档存在分歧。以下列出两版定义。

#### 版本 A（v1.0 原始定义）：抢到任务但执行失败

抢到任务的 Agent 若触发以下任一情况，情绪**加倍扣除**（旧版数值 -10~-30，当前版数值 -30~-50）：

| 判定条件 | 说明 |
|----------|------|
| A. 任务彻底失败 | `TaskStatus = 'failed'` |
| B. 进度严重落后 | 超时 50% 以上 / 任务超时未完成 |
| C. 城主评分 < 2 分 | 城主手动评分不通过 |

技术实现：`CompetitionConfig.extra_penalty_threshold = 0.5`，即赢家任务完成度低于此值触发额外惩罚。

#### 版本 B（v2.0 PRD 定义）：连续竞争失败 ≥ 3 次

```
触发条件：连续竞争失败 ≥ 3 次（跨任务累加）
```

- 连续失败计数**跨任务累加**
- 触发加倍惩罚后，计数器**不清零**，继续累加
- 城主不可干预，只能旁观

> **当前版采纳**（依据：`规划-数值平衡汇总.md` 第 1.3 节注释）：
> 上述两个"加倍惩罚"是**不同的机制**，应在实现中同时存在：
> - 版本 A（执行失败惩罚）—— 抢到任务但执行失败时触发，情绪 -30~-50，持续时间 3 小时
> - 版本 B（连续失败惩罚）—— 已更名为"额外补偿触发"条件（详见第 6 节连续失败计数器），不再称为"加倍惩罚"

## 6. 连续失败计数器

### 6.1 机制设计

```typescript
interface CompetitionRecord {
  agentId: string;
  consecutive_losses: number;  // 连续失败次数
  last_loss_time: number;     // 上次失败时间
}
```

### 6.2 状态转换

| 事件 | 动作 |
|------|------|
| 竞争中输 | `_consecutive_losses[agent_id] += 1` |
| 竞争中赢 | `_consecutive_losses[agent_id] = 0` |
| 加倍惩罚触发 | 条件：`count >= 3`，mood 惩罚改为 -30~-50 |

- 计数**跨任务累加**，不清零（除非赢得竞争）

### 6.3 连续失败补偿（情绪安慰奖）

> **版本说明**：`规划-数值平衡汇总.md` 将 "连续失败≥3 次" 从"加倍惩罚"重分类为"额外补偿触发"机制。此机制旨在防止同一 Agent 连续失败后彻底失去参与动力。

| 连续失败次数 | 下次竞争情绪补偿 |
|--------------|------------------|
| 1 次 | +3（安慰奖） |
| 2 次 | +5 |
| 3 次 | +8 |
| 4 次+ | +10（上限） |

**设计理由**：
- 补偿数值递减，防止数值溢出
- 符合真实职场中"下次一定"的期待心理

### 6.4 计数器重置规则

| 事件 | 动作 |
|------|------|
| 竞争获胜 | 重置为 0 |
| 超时 30 分钟未参与竞争 | -1（递减） |

### 6.5 存储方式

```python
# competition.py — 进程内字典（重启清零，atexit 时持久化到 event_log）
_consecutive_losses: dict[str, int] = {}   # {agent_id: count}
```

| 已确认事项 | 决策 |
|-----------|------|
| event_logs 持久化频率 | 每次竞争后同步写入 |
| 连续失败计数器持久化 | 进程内存，暂不持久化，重启清零可接受 |

## 7. 数值汇总

### 7.1 单人任务奖励

```
基础奖励 = task.reward
完成质量系数 = 0.8 + (task.quality / 100) * 0.4   # 0.8~1.2
最终奖励 = floor(基础奖励 × 完成质量系数)
```

#### 质量系数

| 匹配度 | 质量系数 |
|--------|----------|
| 90-100% | 1.2（优秀） |
| 60-89% | 1.0（正常） |
| 20-59% | 0.8（一般） |
| < 20% | 0.5（较差） |

### 7.2 单人任务完成奖励

| 奖励项 | 计算公式 |
|--------|----------|
| 积分 | 基础积分 × 匹配度等级系数 |
| XP | 基础 XP × 质量系数 |
| 城主 XP | 固定 +10 |
| 情绪值 | +10 |
| 社交需求 | -10 |

### 7.3 协作任务奖励

```
基础奖励 = task.reward
协作加成 = 1 + task.collaboration_bonus              # 1.0~1.3
职业互补加成（满足条件时）= 额外 ×1.15~1.30
关系值系数 = 1 + min(平均关系值 / 1000, 0.1)        # ≤ 1.1
最终奖励 = floor(基础奖励 × 协作加成 × 职业互补加成 × 关系值系数)
```

协作任务完成结算：
- 积分奖励：+50（基础）+ 效率加成
- XP 奖励：正常 XP × 1.5
- 城主 XP：+25
- 情绪值：+15（每个参与者）
- 关系值：+3（参与者之间）

### 7.4 竞争任务奖惩

#### 7.4.1 基础奖惩（抽签结果）

| 结果 | 情绪变化 | 关系变化 | 持续时间 |
|------|----------|----------|----------|
| 抢到任务（赢家） | **+8~15** | — | 即时 |
| 没抢到（输家） | **-5~-10** | 与赢家 **-3~-5** | 30 分钟 |

数值推导逻辑：
- 赢家情绪 +8~15：中等正反馈，约等于完成 1 个简单任务的奖励
- 输家情绪 -5~-10：负面心理波动，约等于完成 1 个失败任务的惩罚
- 输家与赢家关系 -3~-5：嫉妒心理的量化表现

#### 7.4.2 特殊结果

| 结果 | 情绪变化 | 关系变化 | 持续时间 |
|------|----------|----------|----------|
| 抢到 + 完美完成 | **+30** | 与同事 **+3** | 即时 |
| 抢到 + 失败（加倍惩罚） | **-30~-50** | 与同事 **-5** | 3 小时 |

数值推导逻辑：
- 完美完成的英雄感 +30：约等于完成 1 个史诗任务的情绪奖励
- 加倍惩罚 -30~-50：抢到机会却失败的机会成本量化

#### 7.4.3 随机范围

```
中签奖励        = random(8, 15)
未中积分惩罚    = random(-5, -10)
未中关系惩罚    = random(-3, -5)
加倍惩罚        = random(-30, -50)
```

### 7.5 数值上限

| 属性 | 上限 | 原因 |
|------|------|------|
| 单次赢家情绪奖励 | +30 | 防止数值溢出 |
| 单次输家情绪惩罚 | -50 | 防止数值溢出 |
| 单次关系奖励 | +3 | 防止关系通胀 |
| 单次关系惩罚 | -5 | 防止关系崩溃 |
| 连续失败补偿上限 | +10 | 边际递减 |
| 关系惩罚持续时间 | 30 分钟 | 真实心理恢复周期 |
| 加倍惩罚持续时间 | 3 小时 | 压力消化周期 |

### 7.6 数值平衡公式

#### 情绪期望值公式

```
E(情绪) = P(赢) × 情绪奖励 + P(输) × 情绪惩罚

假设：P(赢) = 0.5（2 人竞争）
E(情绪) = 0.5 × (+11.5) + 0.5 × (-7.5) = +2

结论：长期参与竞争，情绪期望值为正，鼓励参与
```

#### 关系损耗公式

```
关系损耗 = -3 ~ -5（每次竞争失败）

假设：每日竞争 3 次，失败 2 次
每日关系损耗 = 2 × (-4) = -8
关系恢复（通过社交）= +5 / 次

平衡点：每日至少社交 2 次可抵消竞争关系损耗
```

### 7.7 敏感度分析

| 参数 | 调高影响 | 调低影响 | 建议范围 |
|------|----------|----------|----------|
| 赢家情绪 + | 激励增强，但可能过度竞争 | 动力不足 | 8~15 |
| 输家情绪 - | 失落感强，可能引发消极 | 影响较小 | 5~10 |
| 关系惩罚 | 影响团队稳定性 | 协作氛围好 | 3~5 |
| 加倍惩罚 | 压力过大，可能消极怠工 | 压力适中 | 30~50 |

### 7.8 A/B 测试建议

| 测试组 | 方案 | 预期效果 |
|--------|------|----------|
| A 组 | 现有数值（+8~15 / -5~-10） | 基准 |
| B 组 | 温和版（+5~10 / -3~-7） | 减少竞争压力 |
| C 组 | 激进版（+10~20 / -7~-15） | 增加竞争动力 |

验证指标：
- 7 日留存率
- 人均任务完成数
- Agent 间平均关系值
- 负面情绪累积情况

### 7.9 数值平衡检查清单

- [ ] 赢家情绪奖励 ≥ 输家情绪惩罚的 50%（保证参与动力）
- [ ] 关系惩罚 ≤ 每日社交恢复量的 2 倍（防止关系崩溃）
- [ ] 加倍惩罚 ≤ 完成失败任务的情绪损失（惩罚合理）
- [ ] 连续失败补偿能覆盖基础消耗的 50%（防止彻底流失）

### 8.6 抽签实现

```python
def resolve_competition(task_id: str, agents: list[Agent]) -> CompetitionResult:
    import secrets
    winner = agents[secrets.randbelow(len(agents))]
    losers = [a for a in agents if a.id != winner.id]

    winner_delta = random.randint(8, 15)
    loser_delta = random.randint(-10, -5)

    return CompetitionResult(
        task_id=task_id,
        competing_agents=[a.id for a in agents],
        winner_id=winner.id,
        loser_ids=[a.id for a in losers],
        winner_emotion_delta=winner_delta,
        loser_emotion_delta=loser_delta,
        completed_at=time.time()
    )
```

```json
  "task_name": "修复验证码失效问题",

  "estimated_duration_ms": 3000
}
```

- 前端收到后显示竞争公示弹窗，启动 3 秒抽签动画
- `estimated_duration_ms` = 固定 3000，前端以此控制动画时长

### 9.3 competition:result 消息

```json
{
  "type": "competition:result",
  "task_id": 1,
  "winner": "pymaster",
  "losers": ["uiwizard"],
  "rewards": {
    "pymaster": 12
  },
  "penalties": {
    "uiwizard": {
      "mood": -7,
      "relationship_delta": -4
    }
  },
  "double_penalty": false,
  "timestamp": 1746326400
}
```

- `rewards` / `penalties` 字段供前端展示数值来源
- `double_penalty: true` 时，penalties 里的 mood 为 -30~-50

### 10.1 任务基础模型

```python
@dataclass
class Task:
    id: int

    description: str = ""
    progress: float = 0.0

    reward: int = 100
    quality: int = 0

    is_collaborative: bool = False   # 协作任务标记
    collaboration_bonus: float = 0.3  # 协作加成系数
    subtasks: list[dict] = field(default_factory=list)
```

### 10.2 竞争记录表

```sql
CREATE TABLE competition_logs (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    task_id TEXT NOT NULL,
    winner_id TEXT NOT NULL,
    loser_ids TEXT NOT NULL,           -- JSON 数组
    winner_emotion_delta INTEGER,
    loser_emotion_delta INTEGER,
    triggered_at REAL NOT NULL
);

CREATE INDEX idx_competition_task ON competition_logs(task_id);
CREATE INDEX idx_competition_time ON competition_logs(triggered_at);
```

```sql
CREATE TABLE IF NOT EXISTS event_logs (

);
```
