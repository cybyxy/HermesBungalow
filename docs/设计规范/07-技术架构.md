## 1. 整体架构

### 1.1 核心原则

```
┌─────────────────────────────────────────────────────────────────────┐
│                           架构原则                                    │
├─────────────────────────────────────────────────────────────────────┤
│                                                                      │
│   【后端 - 游戏框架】              【前端 - 展示层】                  │
│   ├── 业务逻辑（100%）             ├── UI 渲染（100%）               │
│   ├── 状态管理（唯一事实来源）      ├── 动画播放                      │
│   ├── 数值计算                      ├── 用户输入捕获                  │
│   ├── AI 推理调用                   └── 音视频播放                    │
│   ├── 任务调度                                                         │
│   ├── 事件系统                     【禁止前端做的】                    │
│   ├── 碰撞检测                      ├── 业务逻辑判断                  │
│   ├── 路径规划                      ├── 状态计算                      │
│   └── 数据存储                      ├── AI 推理                       │
│                                     └── 任务分配                      │
│   【通信方式】                                                          │
```

### 1.2 技术栈概览

| 层级 | 技术 | 选型理由 |
|------|------|----------|
| 前端框架 | React 18+ / Vite | 生态成熟，组件化完善 |
| 语言 | TypeScript | 类型安全，IDE 支持好 |
| 构建工具 | Vite | 快速冷启动，热更新快 |
| **UI 布局** | **纯 React 卡片（CSS Grid）** | **卡片式房间网格，AgentCard/RoomCard 组件** |
| 状态管理 | Zustand | 轻量，TypeScript 友好 |
| 后端框架 | **Starlette** | ASGI 异步服务器（52 条路由） |
| 持久存储 | **SQLite**（`hermes_bungalow.db`） | 轻量、无依赖、适合单机游戏 |
| 通信 | WebSocket + SSE + HTTP REST | 前后端分离架构 |
| LLM 推理 | **hermes-agent**（`~/.hermes/hermes-agent/`） | Agent 对话引擎 + 任务编排 |

> **FastAPI vs Starlette**：原始规划引用 FastAPI 的 `WebSocket` 类与路由装饰器。实际实现已使用 **Starlette** 作为 ASGI 框架。下文代码示例按规划版本保留 FastAPI 风格，实际开发应使用 Starlette 等价 API。

### 1.4 服务职责边界

| 服务 | 进程 | 端口 | 职责 |
|------|------|------|------|
| `server.py` | 游戏主进程 | `:8765` | 游戏状态唯一事实来源（SQLite）、REST API（`/api/task/*`）、WebSocket Gateway（`/ws/gateway`）、Hermes 通用接口（`/api/*`）、LLM 事件标签解析、游戏 Tick 推进、agent_server.py 子进程生命周期管理 |
| `agent_server.py` | per-agent 子进程 | `:8001~` | Hermes Agent 对话推理、SSE 流式输出、Agent 私有会话状态；**不参与游戏状态读写** |

**服务间通信**：
```
前端 ←→ server.py (:8765)
         ├── REST /api/task/*（游戏状态读写）
         ├── WebSocket /ws/gateway（游戏事件推送）
         └── SSE /api/task/agent-chat-orchestrated/stream（Agent 推理流）
              ↕（内部调用）
         agent_server.py (:8001~)（LLM 推理）
```

### 1.5 存储管理设计

> **设计决策**：无存档，实时记录所有状态，无法回档

#### 存储方式

| 项目 | 值 |
|------|-----|
| 数据库 | SQLite（`hermes_bungalow.db`） |
| 用途 | 实时状态持久化（页面刷新后恢复） |
| 限制 | 无玩家存档/读档功能，关闭浏览器=游戏结束 |

#### 存储策略

```
【存储时机】
- 用户每次输入触发 AI 推理时 → 实时写入
- 任务完成/失败时 → 实时写入
- 社交事件发生时 → 实时写入
- 数值变化时 → 实时写入

【读取时机】
- 前端连接时 → 加载最新状态
- 页面刷新时 → 从数据库恢复最新状态

【禁止行为】
- ❌ 玩家手动存档
- ❌ 玩家读档/回档
- ❌ 多存档槽位
```

#### 核心表结构

```sql
-- Agent 状态表
CREATE TABLE agents (
    id TEXT PRIMARY KEY,
    name TEXT NOT NULL,
    profession TEXT NOT NULL,
    energy REAL DEFAULT 100.0,
    focus REAL DEFAULT 100.0,
    social REAL DEFAULT 50.0,
    mood REAL DEFAULT 60.0,
    sleepiness REAL DEFAULT 0.0,
    relationship_main REAL DEFAULT 100.0,
    location TEXT DEFAULT '城主办公室',
    status TEXT DEFAULT 'idle',
    updated_at INTEGER DEFAULT (strftime('%s', 'now'))
);

-- 任务表
CREATE TABLE tasks (
    id TEXT PRIMARY KEY,
    title TEXT NOT NULL,
    description TEXT,
    complexity INTEGER DEFAULT 1,
    required_profession TEXT,
    status TEXT DEFAULT 'pending',
    assignee_id TEXT,
    created_at INTEGER DEFAULT (strftime('%s', 'now')),
    completed_at INTEGER,
    FOREIGN KEY (assignee_id) REFERENCES agents(id)
);

-- 社交关系表
CREATE TABLE relationships (
    id TEXT PRIMARY KEY,
    agent_a_id TEXT NOT NULL,
    agent_b_id TEXT NOT NULL,
    affection REAL DEFAULT 50.0,
    relationship_value REAL DEFAULT 30.0,
    stage TEXT DEFAULT 'stranger',
    last_greet_time INTEGER,
    FOREIGN KEY (agent_a_id) REFERENCES agents(id),
    FOREIGN KEY (agent_b_id) REFERENCES agents(id)
);

-- 事件日志表
CREATE TABLE event_logs (
    id TEXT PRIMARY KEY,
    event_type TEXT NOT NULL,
    agent_id TEXT,
    task_id TEXT,
    content TEXT,
    mood_delta REAL,
    created_at INTEGER DEFAULT (strftime('%s', 'now'))
);

-- 用户输入日志表（AI推理追踪）
CREATE TABLE input_logs (
    id TEXT PRIMARY KEY,
    input_type TEXT NOT NULL,  -- 'normal' or '@mention'
    target_agent_id TEXT,
    content TEXT NOT NULL,
    ai_reasoning TEXT,  -- JSON
    created_at INTEGER DEFAULT (strftime('%s', 'now'))
);
```

### 3.4 WebSocket 服务端处理

> **注意**：以下代码展示规划阶段的 FastAPI 风格。实际实现使用 **Starlette**，`WebSocket` 类和 `send_json` 方法 API 接口相似。

```python
class GameServer:
    def __init__(self):
        self.active_connections: dict[str, WebSocket] = {}
        self.game_state: GameState = GameState()

    async def connect(self, websocket: WebSocket, client_id: str):
        await websocket.accept()
        self.active_connections[client_id] = websocket

    async def disconnect(self, client_id: str):
        del self.active_connections[client_id]

    async def broadcast(self, message: dict):
        for connection in self.active_connections.values():
            await connection.send_json(message)
```

## 5. AI 推理策略

### 5.1 核心原则

| 原则 | 说明 |
|------|------|
| **AI 推理成本高** | 每次调用消耗 Token，有延迟 |
| **本地处理效率高** | 毫秒级响应，无成本 |
| **混合模式** | AI 处理创意/判断，本地处理数值/状态 |
| **尽量减少 AI 调用** | 能本地处理的绝不用 AI |
| **AI 是大脑（做决策），本地是身体（执行动作）** | — |

### 5.4 AI 推理调用频率控制

> **核心考量**：AI 推理消耗 Token，成本高，必须严格控制调用频率

#### 5.4.1 调用频率分级

| 级别 | 调用频率 | 场景 | 优化方式 |
|------|---------|------|----------|
| **独立任务** | 无限制 | 单个 Agent 独立工作 | 正常 AI 推理 |
| **协作交流** | 按需调用 | 需要对话时 | 城主可监听 |
| **行为决策** | 本地优先 | 多 Agent 场景 | 规则判断，异常才 AI |
| **城主技能/事件** | 按需调用 | 必要时 | 正常使用 |

#### 5.4.2 协作交流优化方案

**按需调用，不限制频率**。
```
【协作交流 - 原则】
✅ 需要对话时调用 AI（如：遇到问题需要讨论）
✅ 正常协作时使用本地模板过渡
✅ 城主可以选择监听/参与协作交流
✅ 不人为限制 AI 调用次数，保证协作质量
```

**何时使用本地模板**：
```
【本地模板 - 正常协作过渡】
├── "正在设计中..." / "写代码中..." / "测试中..."
├── "进度 30% / 60% / 90%"
├── "这块我来负责..."
└── "你那边怎么样了？"

【需要 AI 对话时】
├── 遇到问题需要讨论 → AI 生成讨论内容
├── 任务有进展需要同步 → AI 生成同步内容
├── 需要做决策 → AI 生成选项分析
└── 城主参与 → AI 生成城主互动内容
```

**城主参与模式**：
```
【监听模式】
城主选择监听 → AI 生成协作对话内容供城主查看
城主可随时打断参与

【不监听模式】
本地模板显示状态 → 不调用 AI 生成对话内容
节省 token 消耗
```

#### 5.4.3 单个 Agent 独立任务

**单个 Agent 独立任务时 AI 推理不受限制**。
```
【独立任务 - 无频率限制】
├── Agent 独立工作 → 正常 AI 推理
├── 工作过程中 → AI 判断下一步
├── 遇到问题 → AI 分析原因
├── 需要决策 → AI 给出选项
└── 任务完成 → AI 生成总结

【原因】
单个 Agent 独立工作，不会产生多 Agent 的 token 叠加问题
每分钟 1 次 AI 调用 = 60 次/小时 = 正常消耗水平
```

#### 5.4.4 Agent 自主决策优化方案

**问题**：多个 Agent 每 30 秒检测一次，累积 token 消耗巨大。

**优化方案**：**本地规则判断**为主，AI 仅判断异常情况。
```
【Agent 自主决策 - 优化前】
❌ 每个 Agent 每 30 秒调用 1 次 AI 判断
❌ 5 个 Agent = 每 30 秒 5 次 AI 调用
❌ 1 小时 = 600 次 AI 调用

【Agent 自主决策 - 优化后】
✅ 本地规则判断：能量<50？专注力<60？社交需求>70？
✅ 规则判断命中率：90% 的情况不需要 AI
✅ 仅当本地规则无法判断时（如："最近情绪有点低落"）
✅ AI 调用频率：每个 Agent 约 1 次/小时（降低 90%）
```

**本地规则判断示例**：
```
【本地可完全处理的判断】
├── 能量 < 50 → 需要进食/休息
├── 能量 < 30 → 需要紧急休息
├── 专注力 < 60 → 需要咖啡/休息
├── 社交需求 > 70 → 需要社交
├── 睡意 > 80 → 需要睡眠
└── 以上情况 → 直接执行对应行为

【需要 AI 判断的情况 - 极少】
├── 能量和专注力都中等，但效率下降 → 判断原因
├── 社交需求不高，但情绪持续低落 → 判断原因
├── 多个需求同时不满 → 优先级判断
└── 其他复杂情境 → "最近状态不太好"等主观感受
```

#### 5.4.5 缓存策略

```
【可缓存 - 一次生成，多次使用】
├── 打招呼模板（按关系阶段：认识/朋友/挚友）
│   └── 认识："你好。" / 朋友："最近怎么样？" / 挚友："嘿！好久不见！"
├── 职业梗/口头禅
│   └── 设计师："这个颜色..." / 程序员："命名规范..."
├── 闲聊开场白（按性格分类）
│   └── 开朗："今天天气真好" / 内向："嗯..."
└── 协作状态描述模板
    └── "正在设计中..." / "写代码中..." / "测试中..."

【必须实时生成的 - 严格控制】
├── 任务具体内容（每个任务不同）
├── 协作中的具体讨论（任务相关）
├── 事件响应策略（每个事件不同）
└── 城主激励/点评（每次不同）
```

#### 5.4.6 多 Agent 合并调用

```
【问题】
每个 Agent 独立调用 AI，token 消耗 = Agent 数量 × 单次调用

【优化方案】
主 agent 作为协调者，统一收集多个 Agent 的问题
合并为一次 AI 调用返回多个响应

【示例】
❌ 优化前：设计师问"我该做什么？"→ AI 调用 1 次
❌ 优化前：程序员问"我该做什么？"→ AI 调用 1 次
❌ 优化前：测试员问"我该做什么？"→ AI 调用 1 次
    = 3 次 AI 调用

✅ 优化后：3 个 Agent 同时询问 → 主 agent 合并为 1 次调用
✅ 返回：[{Agent: "设计师", task: "..."}, {...}, {...}]
    = 1 次 AI 调用
```

#### 5.4.7 频率控制总结

| 功能 | 调用方式 | 优化说明 |
|------|----------|----------|
| **协作交流** | 按需调用 AI | 遇到问题/需要讨论时调用，正常用本地模板 |
| **Agent 独立任务** | 无频率限制 | 单个 Agent 正常工作，正常 AI 推理 |
| **Agent 行为决策** | 本地规则优先 | 规则判断 90%，异常情况才用 AI |
| **打招呼内容** | 模板缓存 | 本地模板+变量，不实时生成 |
| **多 Agent 询问** | 合并为 1 次 | 主 agent 统一收集，减少 N-1 次调用 |

#### 5.5.4 AI 推理内容（每次输入必执行）

每次用户输入触发 AI 推理时，必须完成以下推理：
```

   - 目标是谁（主 agent 还是指定 agent）？

2. 【状态更新】
   - 相关 Agent 数值变化（能量/专注力/社交/情绪/睡意）
   - 任务状态变化（如有）

3. 【社交影响】
   - 关系值/好感度变化
   - 关系阶段判断

4. 【后续建议】
   - 是否需要提醒用户某些事项
   - 是否需要生成 Agent 响应内容
```

## 6. Agent 编排 SSE 会话

### 6.1 目标

- 推理仅在后端完成；前端通过 **SSE** 实时展示（**仅 reasoning 流式**；工具 `tool_start` + 单条 `tool_end`；最终回复整段 `assistant_message`）。
- **整轮**内除 **POST 创建 run** 与 **POST 取消 stream** 外，**不再**发起编排类 POST；编排循环在服务端完成。
- **同 `step_id` 的多次 `reasoning_delta` 合并为一个气泡**（前端用 `appendToInference` 追加到同一 `InferenceEntry`）。
- 右侧 **RightPanel**：**上** 会话（user / reply / error），**下** 过程与工具（reasoning / status / tool_*）。
- 停止：对已知的 Hermes `stream_id` 调用 **`cancel_stream`**（与 Hermes 引擎一致）。

### 6.2 端点定义

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/task/agent-chat-orchestrated/run` | Body 与现有一致：`agent_id`, `message`, `auto_peer`, `attachments?`。校验后创建 `run_id`，启动后台线程执行编排，立即返回 `{ ok, run_id, work_order_id? }`。 |
| GET | `/api/task/agent-chat-orchestrated/stream?run_id=` | `text/event-stream`，每条 `data: {json}`。 |
| POST | `/api/task/agent-stream/cancel` | Body `{ "stream_id": "..." }`，内部 `cancel_stream(stream_id)`。 |

> 详细 API 定义请参见 **`docs/API_CONTRACTS.md`** 第五章节「游戏编排 SSE」，本章节的 API 定义以此为最终权威。

### 6.3 SSE 事件类型

公共字段：`run_id`, `seq`（单调递增）, `type`。

| type | 方向 | 说明 |
|------|------|------|
| `step_begin` | Server→Client | 新一步 LLM：`step_id`, `agent_id`, `stream_id`（供取消） |
| `reasoning_delta` | Server→Client | 追加文本：`step_id`, `agent_id`, `text`（前端追加到同一 `InferenceEntry`） |
| `tool_start` | Server→Client | `agent_id`, `step_id`, `name`, `args_summary?` |
| `tool_end` | Server→Client | `agent_id`, `step_id`, `name`, `ok`, `result_summary?`, `error?` |
| `assistant_message` | Server→Client | 整段回复：`agent_id`, `step_id`, `markdown` |
| `step_done` | Server→Client | 本步结束：`step_id`, `agent_id` |
| `delegation_start` | Server→Client | `from_agent_id`, `to_agent_id`, `reason?` |
| `error` | Server→Client | `message`, `fatal?` |
| `stopped` | Server→Client | 用户取消：`step_id?`, `agent_id?` |
| `turn_done` | Server→Client | 整轮结束（前端解锁输入） |

### 6.4 前端行为

1. `submitStudioChat`：用户消息写入 log 后 → `POST .../run` → `EventSource` GET `.../stream?run_id=`。
2. 维护 `stepId -> inferenceEntryId`（仅 `reasoning`）：
   - `step_begin` 创建空 reasoning 气泡并记录映射
   - `reasoning_delta` 用 `appendToInference` 追加
   - `step_done` 删除映射
3. 停止：`POST .../agent-stream/cancel`，body 为最近收到的 `stream_id`（来自 `step_begin`）。
4. `RightPanel`：单栏上下分区；`inferenceLog` 按 variant 过滤到「会话」或「过程与工具」列表。

### 6.5 后端实现要点

- `agent.py`：`sync_session_turn` / `_drain_agent_stream` / `run_recursive_peer_invokes` / `orchestrated_peer_turns_sync` 增加可选 `event_sink`（线程内同步 `put` 到 `queue`）与 `run_id`；不改变无 `event_sink` 时的 JSON 行为。
- `server.py`：`RUNS` 内存表 + 三路由；`monitor_*` 与现有一致。

### 6.6 风险

- 进程重启丢失 `run_id`（仅内存）；生产可换 Redis。
- EventSource 跨域需 cookie/同源；开发走 Vite 代理。

## 7. WebSocket 通信协议

> **重要说明**：以下 WebSocket 消息类型来源于规划文档，**`docs/API_CONTRACTS.md`** 第二章「Gateway WebSocket」为实际实现的最终权威来源。本章节以规划版消息类型为主体，与 API_CONTRACTS.md 存在以下差异：
> - 规划版使用 `type` 字段直接定址（如 `agent:move`）；API_CONTRACTS.md 使用频道订阅机制（`game_event` + `channel`）。
> - 规划版属于早期设计，API_CONTRACTS.md 为演进的正式版本。

### 7.1 消息类型定义（规划版）

#### 后端 → 前端

```typescript
type ServerMessage =
  | { type: 'state:init'; data: GameState }
  | { type: 'state:snapshot'; data: GameSnapshot }
  | { type: 'agent:update'; agentId: string; changes: Partial<AgentState> }
  | { type: 'agent:move'; agentId: string; path: Position[] }
  | { type: 'agent:emotion'; agentId: string; emotion: string; bubble: string }
  | { type: 'task:update'; taskId: string; changes: Partial<TaskState> }
  | { type: 'task:complete'; taskId: string; result: TaskResult }
  | { type: 'social:greeting'; agentA: string; agentB: string; content: string }
  | { type: 'social:collab'; agents: string[]; content: string }
  | { type: 'social:share'; giver: string; receiver: string; item: string }
  | { type: 'event:trigger'; event: GameEvent }
  | { type: 'competition:start'; agents: string[] }
  | { type: 'competition:result'; winner: string; losers: string[] }
  | { type: 'skill:used'; skillId: string; target: string }
  | { type: 'notification'; level: 'info'|'warn'|'error'; message: string }
```

#### 前端 → 后端

```typescript
type ClientMessage =
  | { type: 'citylord:assign_task'; taskId: string; agentId: string }
  | { type: 'citylord:use_skill'; skillId: string; targetId?: string }
  | { type: 'citylord:intervene'; agentId: string; action: string }
  | { type: 'citylord:listen:toggle'; enabled: boolean }
  | { type: 'citylord:respond'; eventId: string; choice: number }
  | { type: 'chat:message'; content: string }
```

### 7.2 Gateway WebSocket 消息类型（API_CONTRACTS.md 正式版）

#### 客户端 → 服务端

| type | 字段 | 说明 |
|------|------|------|
| `chat` | `message` | 聊天（演示：回显 + 可选解析标签） |
| `game_event_sub` | `channels` | 订阅频道数组 |
| `ping` | — | 心跳 |
| `sync_request` | `last_seq` | 重连后请求增量同步（可选） |

#### 服务端 → 客户端

| type | 字段 | 说明 |
|------|------|------|
| `chat_stream` | `delta` | 流式片段（演示） |
| `chat_done` | `final_content` | 聊天结束 |
| `game_event` | `channel`, `data`, `seq` | 游戏事件推送（含序列号） |
| `state:snapshot` | `data`, `snapshot_seq` | 全量状态快照 |
| `pong` | — | 心跳响应 |
| `error` | `code`, `message` | 错误信息 |
| `payload_too_large` | `size` | 消息超限 |

#### 游戏事件频道

| channel | 说明 | 优先级 |
|---------|------|--------|
| `competition` | 任务竞争结果 | P0 |
| `social` | 打招呼 / 社交 | P0 |
| `task` | 任务状态变更 | P0 |
| `agent_status` | Agent 状态变更（移动/情绪/数值） | P0/P1 |

### 7.3 状态版本控制

| 字段 | 说明 | 用途 |
|------|------|------|
| `seq` | 消息序列号（整数，从 1 开始单调递增） | 检测消息丢失/乱序 |
| `snapshot_seq` | 最近一次 `state:snapshot` 的序列号 | 客户端请求增量同步基准 |

**重连流程**：
1. 客户端记录最后收到的 `seq`
2. 连接后发送 `{type: "sync_request", last_seq: N}`（可选）
3. 服务端返回 `state:snapshot`（`seq = snapshot_seq`）用于全量同步
4. 缺失消息通过 `state:snapshot` 补齐，不单独补发中间消息

### 7.4 心跳与超时

| 配置 | 值 |
|------|-----|
| 客户端 ping 间隔 | 30 秒 |
| 服务端 pong 响应 | 立即 |
| 连接超时阈值 | 60 秒无消息则断开 |
| 重连策略 | 指数退避（1s → 2s → 4s → 8s → max 30s） |

### 7.5 推送频率控制

| 优先级 | 触发条件 | 推送时机 |
|--------|----------|----------|
| **P0 高** | Agent 移动、任务状态变更、事件触发、通知 | 状态变化时立即推送 |
| **P1 中** | 数值变化（能量/专注力/情绪）、冷却状态 | 每秒最多 1 次（防刷） |
| **P2 低** | 完整状态快照（初始化/手动刷新） | 按需，限制频率 |

**防刷机制**：同一 `agent_id` 的高频属性变更（P1）合并为批量消息，单帧最多承载 10 个属性变更。

### 7.6 错误处理与降级

| 错误类型 | 错误码 | 前端处理 |
|----------|--------|----------|
| 消息超限 | `payload_too_large` | 分帧发送或请求快照 |
| 连接超时 | `timeout` | 指数退避重连 |
| 序列号跳跃 | `seq_mismatch` | 请求全量 `state:snapshot` |
| 服务不可用 | `service_unavailable` | 显示维护提示 |

### 7.7 单帧限制

单帧文本消息建议不超过 **64KB**（超出返回 `payload_too_large`）。

## 附录 A：FastAPI vs Starlette 差异说明

原始规划文档（`规划-Hermes数字工作室技术架构.md` v2.0）中，后端框架引用为 **FastAPI**，代码示例使用：
```python
from fastapi import WebSocket
```

实际实现已迁移至 **Starlette**。主要差异点：

| 方面 | FastAPI（规划） | Starlette（实现） |
|------|----------------|-------------------|
| WebSocket 类 | `fastapi.WebSocket` | `starlette.websockets.WebSocket` |
| 路由注册 | `@app.websocket("/ws")` | `@app.websocket_route("/ws")` |
| 请求/响应 | `fastapi.Request` / `fastapi.Response` | `starlette.requests.Request` / `starlette.responses.Response` |
| 路由表 | 装饰器自动注册 | `routes = [Route(...), WebSocketRoute(...)]` |

**实际开发应使用 Starlette API。**
