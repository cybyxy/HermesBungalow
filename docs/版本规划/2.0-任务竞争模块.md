## 1. v2.0 版本概述

### 1.1 v2.0 定位

本版本在 v1.0 单人任务 + 协作任务基础上，引入 **任务竞争机制（Task Competition）**，解决"同职业多个 Agent 空闲时任务归谁"的问题。核心思路：**纯公平抽签、城主不干预、奖惩绑定情绪与关系值**。

### 1.2 v2.0 版本范围

| 模块 | 变更 | 优先级 |
|------|------|--------|
| 任务系统 | 扩展为三种模式：单人 / 协作 / 竞争 | P0 |
| 竞争模块（新增） | 抽签、奖惩、连续失败计数 | P0 |
| WebSocket 消息 | 新增 `competition:*` 消息类型 | P0 |
| 前端弹窗 | 竞争公示弹窗（复用 PopupSheet） | P0 |
| 抽签动画 | 固定 3 秒动画展示 | P0 |
| 数值系统 | 引入情绪/关系值奖惩模型 | P1 |
| event_logs | 竞争记录写入 event_logs | P1 |
| 连续失败补偿 | 安慰奖机制 | P1 |

### 1.3 v2.0 非范围（v2.x 规划）

- 竞争加权抽签（如按等级 / 关系值加权）
- 城主主动干预抽签结果
- 竞争任务超时重抽机制
- Agent 主动放弃竞争资格
- 复杂粒子动画

## 2. 核心变化：v1.0 → v2.0

| 维度 | v1.0 | v2.0 |
|------|------|------|
| 任务分配 | 城主指派 / 简单自动分配 | 引入竞争抽签分配 |
| 多人同职业场景 | 无特殊处理，由城主手动调配 | 自动触发公平抽签 |
| Agent 心理模型 | 关系值影响互动 | 新增情绪值 + 关系值双轨惩罚 |
| 城主角色 | 可干预分配 | 纯旁观，不可干预抽签 |
| 任务系统 | 单人 + 协作 | 单人 + 协作 + 竞争 |
| 数值维度 | 积分奖励为主 | 引入情绪波动 + 关系损伤 |
| WebSocket 消息 | `task:update` | 新增 `competition:start` / `competition:result` |

## 3. 模块全景

### 3.1 任务类型分类（v2.0 完整版）

```
任务类型
 ├── 单人任务：只需1人，城主指派或自动评分分配，无竞争
 ├── 协作任务：is_collaborative=True，需多人，城主指派，有职业互补加成
 └── 竞争任务（新增）：同职业≥2空闲Agent+多人举手，抽签决定归属
```

### 3.2 竞争模块触发条件

三者**同时满足**时触发：

1. **任务只需 1 人执行**：`task.required_agents == 1` 且 `task.is_collaborative == False`
2. **同职业 ≥ 2 名 Agent 空闲**：`agent.status == 'idle'` 且 `agent.current_task is None`
3. **多个 Agent 举手**：Agent 检测到匹配任务时自动举手

### 3.3 竞争流程概要（完整流程见 设计规范/03-任务与竞争系统.md）

```
[任务发布]
    ↓
[触发检测] → 不满足 → 正常分配
    ↓ 满足
[competition:start 广播] → 前端展示竞争公示弹窗
    ↓
[抽签] → secrets.randbelow 纯随机，3秒动画
    ↓
[competition:result 广播] → 赢家/输家、奖惩明细
    ↓
[积分结算] → 情绪值 + 关系值更新
    ↓
[event_logs 记录] → 类型 competition_result
```

## 4. 决策日志

### 4.1 竞争机制决策（2026-05-03）

来源：`规划/v2.0规划讨论区.md`

**参会人**：顾言卿（需求）、江定策（策略架构）、崽崽（城主拍板）

| 决策点 | 选项 | 拍板结果 | 理由 |
|--------|------|----------|------|
| **城主干预权** | A 可干预 / B 不可干预 | **B 不可干预，只可旁观** | 真实职场城主也无法强行指派，让机制自己跑 |
| **抽签是否加权** | A 纯公平 / B 按关系值加权 | **A 纯公平（等概率）** | 运气也是能力，制度面前人人平等 |
| **竞争失败惩罚范围** | A 仅情绪/关系 / B 含能量 | **A 仅情绪/关系** | 能量惩罚过重会打击积极性，现阶不加 |
| **加倍惩罚条件** | A 连续失败≥3次 / B 任务失败 | **B 任务失败/超时/低评分** | 加倍针对机会浪费而非运气差 |
| **连续失败计数** | A 跨任务累加 / B 单任务 | **A 跨任务累加，不清零** | 保持惩罚压力 |
| **动画时长** | A 可配置 / B 固定3秒 | **B 固定3秒，不可配置** | 统一体验，防止前端透配 |

### 4.2 任务系统决策（2026-05-04）

来源：`HermesBungalow2/规划-任务系统.md`

| 决策点 | 拍板结果 | 理由 |
|--------|----------|------|
| 协作任务最小人数 | **2人起** | 鼓励小规模协作，降低准入门槛 |
| 任务超时机制 | **超时扣50%奖励** | 避免消极磨工 |
| Agent 能否拒绝任务 | **能量<20%时允许拒绝，扣关系值-5** | 避免滥用拒绝权 |
| 竞争举手可撤销？ | **不可撤销** | 保证抽签公平性，公示期前必须参与 |
| 单人任务分配算法 | 能量×0.3 + 专注×0.2 + 职业×0.4 + 关系加成≤0.1 | 职业匹配权重最高 |

### 4.3 技术决策（2026-05-04）

来源：`HermesBungalow2/设计-后端API架构.md`

| 决策点 | 决策 | 理由 |
|--------|------|------|
| 随机数生成 | 生产：`secrets.randbelow` / 调试：环境变量启用固定种子 | 生产不可预测，调试可复现 |
| event_logs 持久化 | 每次竞争后同步写入 | 竞争非高频，数据完整性优先 |
| 连续失败计数器 | 进程内存，暂不持久化 | 重启清零可接受，不影响核心逻辑 |
| WebSocket | service.py 直接广播，gateway 暂不独立 | v2.0 不拆分进程 |

## 5. 数值平衡概要

### 5.1 核心数值一览

| 事件 | 情绪变化 | 关系变化 |
|------|----------|----------|
| 抢到任务（赢家） | +8 ~ +15 | — |
| 没抢到（输家） | -5 ~ -10 | 与赢家 -3 ~ -5 |
| 抢到 + 完美完成 | **+30**（英雄感） | 与同事 **+3** |
| 抢到 + 失败（加倍惩罚） | **-30 ~ -50** | 与同事 **-5** |
| 连续失败补偿 | +3 ~ +10（递增） | — |

### 5.2 加倍惩罚触发条件（任务失败）

- 任务彻底失败（TaskStatus = 'failed'）
- 进度严重落后（超时 50% 以上）
- 城主评分 < 2 分

### 5.3 连续失败补偿

| 连续失败次数 | 下次情绪补偿 |
|-------------|--------------|
| 1次 | +3 |
| 2次 | +5 |
| 3次 | +8 |
| 4次+ | +10（上限） |

- 获胜后重置为 0
- 30 分钟未参与竞争递减 1

### 5.4 关键平衡约束

- 赢家情绪奖励 ≥ 输家情绪惩罚的 50%（保证参与动力）
- 关系惩罚 ≤ 每日社交恢复量的 2 倍（防止关系崩溃）
- 加倍惩罚 ≤ 完成失败任务的情绪损失（惩罚合理）
- 情绪期望值（2人竞争）：E(情绪) = 0.5 × (+11.5) + 0.5 × (-7.5) = **+2**（长期为正）

> **详细数值模型**见 `HermesBungalow2/规划-数值平衡汇总.md`

## 6. 技术架构决策

### 6.1 模块结构

```
backend/api/task/
├── service.py        # 任务服务（assign_task 主入口）
├── competition.py    # 竞争逻辑（新增）
│   ├── resolve_competition()    # 抽签 + 奖惩计算
│   ├── run_lottery()            # 密码学安全抽签
│   ├── record_win/loss()        # 连续失败计数
│   └── _broadcast()             # WebSocket 广播
├── models.py         # 数据模型
└── persistence.py    # 持久化
```

### 6.2 WebSocket 消息

| 消息类型 | 方向 | 触发时机 |
|----------|------|----------|
| `competition:start` | 后端 → 前端 | 竞争开始，含任务名、参与者列表、3秒计时 |
| `competition:result` | 后端 → 前端 | 结果公示，含赢家/输家/奖惩明细/是否加倍惩罚 |

### 6.3 集成方式

- service.py 的 `assign_task()` 检测竞争触发条件
- 满足则调用 `competition.py`，不满足走原有单人/协作流程
- 广播走现有 WebSocket 连接，gateway 暂不独立

## 7. 里程碑与验收标准

### 7.1 里程碑

| 里程碑 | 内容 | 预计 |
|--------|------|------|
| M1 | 竞争模块基础逻辑（抽签 + 奖惩 + 计数） | 开发中 |
| M2 | WebSocket 广播 + 前端竞争弹窗 | 待启动 |
| M3 | 抽签动画 + 连续失败补偿 UI | 待启动 |
| M4 | event_logs 竞争记录 + 统计面板 | 待启动 |
| M5 | 完整集成测试 + 数值调优 | 待启动 |

### 7.2 验收标准

- [ ] 同职业 ≥ 2 空闲 Agent + 非协作任务时，竞争逻辑被触发
- [ ] 抽签结果纯随机，无偏袒（可经统计验证）
- [ ] 赢家/输家情绪值变化符合数值设计
- [ ] 加倍惩罚在任务失败/超时/低评分时正确触发
- [ ] 连续失败计数器跨任务累加，获胜后重置
- [ ] 连续失败补偿正确发放（+3 ~ +10）
- [ ] 竞争结果通过 WebSocket 广播给所有在线客户端
- [ ] 竞争记录写入 event_logs 表，类型 `competition_result`
- [ ] 前端竞争公示弹窗 3 秒动画展示（宣布→抽签→结果）
- [ ] 城主只能查看，无法干预抽签结果
- [ ] 举手后不可撤销
