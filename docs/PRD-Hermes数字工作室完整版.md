## 一、项目概述

### 1.1 游戏定位

Hermes 数字工作室是一款多Agent养成经营游戏，玩家扮演城主，管理一群子Agent。

**初始状态**：游戏开始时只有主agent（城主）一个Agent

**Agent来源**：其他Agent通过用户配置Hermes Profile来生成。用户可以在Hermes系统中配置新的Agent Profile（如：设计师、程序员、测试员、分析师等），配置完成后该Agent会出现在基地中。

### 1.2 核心玩法

| 核心循环 | 说明 |
|----------|------|
| 任务分配 | 从任务池分配任务给Agent |
| Agent养成 | 升级、技能树、关系维护 |
| 社交互动 | 打招呼、协作、社交活动 |
| 城主技能 | 主动影响游戏进程 |

### 1.3 核心循环闭环流程

```
┌─────────────────────────────────────────────────────────────────┐
│                         核心循环闭环                             │
│                                                                 │
│    ┌──────────┐     任务完成      ┌──────────┐               │
│    │  任务池   │ ──────────────→  │  奖励结算  │               │
│    └────┬─────┘                  └────┬─────┘               │
│         │ 分配任务                      │ 积分/XP/社交          │
│         ▼                             ▼                       │
│    ┌──────────┐   城主技能    ┌──────────┐                   │
│    │ Agent执行 │ ←─────────── │ 城主干预  │                   │
│    └────┬─────┘   激励/调度   └──────────┘                   │
│         │ 工作消耗                                                     │
│         ▼                                                           │
│    ┌──────────┐   社交需求↑  ┌──────────┐                   │
│    │ 状态下降  │ ──────────→  │ 社交互动  │                   │
│    │ 饱食度↓   │              │ 打招呼/协作│                   │
│    │ 社交需求↑ │              └────┬─────┘                   │
│    └────┬─────┘                   │ 关系↑/社交需求↓           │
│         │                         ▼                           │
│         └─────── 需要休息 ←─────┘                            │
│                    │                                          │
│                    ▼                                          │
│              ┌──────────┐                                    │
│              │ 恢复设施  │ ← 城主使用"激励演说"加速恢复       │
│              │ 咖啡机/   │                                    │
│              │ 休息室    │                                    │
│              └──────────┘                                    │
│                    │ 状态恢复                                  │
└────────────────────┼────────────────────────────────────────────┘
                     ▼
              ┌──────────┐
              │ 继续任务  │
              └──────────┘
```

**闭环驱动关系**：

| 驱动关系 | 说明 |
|----------|------|
| 任务→奖励 | 完成分配任务获得积分/XP，用于升级城主技能 |
| 奖励→养成 | 城主升级可解锁更强技能（精准分配、灵感赐予等） |
| 工作→消耗 | Agent执行任务消耗饱食度/电量，产生社交需求 |
| 消耗→社交 | 社交需求积累触发打招呼/协作，恢复关系 |
| 社交→效率 | 关系好的Agent协作效率+15%，形成正向循环 |
| 城主→加速 | 城主技能（激励演说）可加速Agent状态恢复 |
| 恢复→任务 | 状态恢复后Agent可继续执行任务 |

| 技能 | 图标 | 冷却 | 效果 |
|------|------|------|------|

| 资源调度 | 💰 | 5秒 | 单体：Token配额+50%，消耗50积分 |
| 灵感赐予 | 🔮 | 7秒 | 协作：质量+15%，进度+10%，消耗30积分 |

## 四、Agent系统

### 4.1 Agent来源

**初始Agent**：游戏开始时只有主agent（城主）

**其他Agent**：通过用户配置Hermes Profile来生成。用户可以在Hermes系统中配置新的Agent Profile（包含：名字、角色、性格、头像、默认工作房间等），配置完成后该Agent会出现在基地中。

### 4.2 Agent角色配置

| Agent | 职业 | 性格 | 口头禅 |
|-------|------|------|--------|
| 主agent | 城主 | 温暖细心 | "大家好，我是主agent！" |
| 小美 | 设计师(示例) | 追求完美 | "这个颜色不太对..." |
| 阿猿 | 程序员(示例) | 逻辑严谨 | "命名强迫症犯了" |
| 点点 | 测试员(示例) | 细心耐心 | "我来给你找点bug" |
| 数据帝 | 分析师(示例) | 理性冷静 | "让我查一下数据" |

> **说明**：职业类型不固定，从用户配置的Hermes Profile提取得到。以上为示例职业。

**数据来源**：Agent角色来自 Hermes Profile 配置（非硬编码），每个Agent包含以下属性：
- `id`: 唯一标识符
- `name`: 显示名称
- `gender`: 性别（male / female / random，用户指定或随机）
- `role`: 职业类型
- `personality`: 性格描述
- `avatar`: 头像资源路径（根据性别加载）
- `pixelArt`: 像素立绘路径（根据性别加载）
- `defaultWorkSpace`: 默认工作房间
- `greetingStyle`: 打招呼风格
- `catchphrase`: 口头禅
- `memes`: 已解锁的梗列表

## 五、任务系统

### 5.1 任务类型

> **说明**：任务类型不固定，根据用户的使用场景或描述，通过推理模型动态生成。

**任务来源**：
- 用户描述需求 → 推理模型解析 → 生成任务类型
- 或用户直接指定任务类型

**匹配度基准**：
> 任务类型与Agent职业的匹配度由推理模型根据实际情况判断。

| 示例任务类型 | 说明 |
|--------------|------|
| 设计任务 | UI/UX设计相关 |
| 编码任务 | 程序开发相关 |
| 测试任务 | 测试验证相关 |
| 分析任务 | 数据分析相关 |

> 以上为示例任务类型，实际任务类型由推理模型根据用户描述和使用场景动态生成。

#### 按难度分类

| 难度 | 星级 | 基础积分 | 基础XP | 完成时间 |
|------|------|----------|--------|---------------|
| 简单 | ★ | 10-15 | 20 | 1 |
| 普通 | ★★ | 20-30 | 50 | 2-3 |
| 困难 | ★★★ | 40-50 | 100 | 4-5 |
| 史诗 | ★★★★ | 80-100 | 200 | 6+ |

### 5.2 任务执行

#### 匹配度效果

| 匹配度 | 效率修正 | 质量修正 | 特殊效果 |
|--------|----------|----------|----------|
| 90-100% | +30% | +20% | 无 |
| 60-89% | ±0% | ±0% | 无 |
| 20-59% | -30% | -20% | 匹配度持续下降 |
| <20% | -60% | - | 触发消极怠工 |

**执行消耗**（真实人类生理版）：

| 消耗项 | 数值/秒 | 说明 |
|--------|---------|------|
| 饱食度 | **-0.5** | 工作消耗，约25-45秒后需休息 |
| 社交需求 | **+0.3** | 工作时孤独感缓慢累积 |

**社交需求惩罚（分级）**：

| 社交需求 | 状态 | 效果 |
|---------|------|------|
| 31-50 | 轻微孤独 | 工作质量-10% |
| 51-70 | 孤独 | 工作质量-20%，情绪-0.5/秒 |
| 71-85 | 严重孤独 | 工作质量-30%，情绪-1/秒 |
| 86-100 | 极度孤独 | 工作质量-40%，情绪-2/秒 |

> **设计理念**：基于番茄工作法（25分钟工作+5分钟休息）和Ultradian Rhythm（90分钟高专注）的真实人类工作节奏

### 5.3 协作任务

**触发流程**：
```
用户描述需求
    ↓
推理模型分析任务复杂度
    ↓
判断是否需要协作（多职业配合/高难度）
    ↓
主agent自动分配协作任务
    ↓
相关Agent收到任务通知
```

**协作判定规则**：

| 条件 | 判断结果 | 说明 |
|------|----------|------|
| 任务涉及多职业 | 需协作 | 设计+开发、测试+分析等 |
| 难度≥★★★ | 需协作 | 史诗任务强制协作 |
| 单Agent能力不足 | 需协作 | 推理模型判断 |
| 同职业任务过多 | 分流协作 | 避免单Agent过载 |

**协作任务分配**：

| 角色 | 职责 | 说明 |
|------|------|------|
| 主Agent（城主） | 协调分配 | 根据推理结果自动分配 |
| 干系Agent | 执行+汇报 | 参与任务的Agent |

**加成条件**：

| 加成条件 | 效果 |
|----------|------|
| 双Agent协作 | 效率+30%，总Token消耗-20% |
| 关系值≥80% | 额外效率+15% |
| 职业互补 | 额外质量+20% |

### 5.4 任务完成

| 项目 | 说明 |
|------|------|
| 完成条件 | 进度达到100% |
| 汇报流程 | **层层汇报**：先干系Agent交流 → 逐级向上汇报 → 至主agent |
| 汇报要求 | 无法跳过 |

**层层汇报流程**：
```
任务完成
  ↓
干系Agent交流（相关参与任务的Agent）
  ↓
逐级向上汇报
  ↓
主agent
```

**汇报排队机制**：
- 多Agent同时需要汇报时，按先到先得原则排队
- 城主办公室同时只能有1个Agent汇报
- 其他Agent在门口等待队列中（FIFO）
- 排队超时60秒后重新尝试

**完成奖励**：积分、XP、城主XP、情绪值、社交需求恢复

### 5.5 任务竞争机制

> **真实职场模拟**：真实职场中，同事之间会因为项目机会产生竞争，有竞争就有心理波动

**触发条件**：
| 条件 | 说明 |
|------|------|
| 主agent判定 | 任务只需1人 |
| 同职业Agent | 场景中存在≥2个同类空闲Agent |
| 多个"举手" | Agent通过AI判断主动竞争 |
| 非协作任务 | 协作者任务不触发竞争 |

**竞争方式**：
- **公平抽签**：每个举手Agent等概率中签（**无加权**），保持公平
- 真实职场中，有时能力强的未必能抢到任务，有运气成分

**竞争过程可见性**：
```
【竞争】设计师{AgentA}和{AgentB}同时举手抢任务
    → 抽签中...（显示3秒思考动画）
    → 🎉 {AgentA}抢到了！显示"我来！"气泡（5秒）
    → 😔 {AgentB}没抢到，显示"下次再..."气泡（5秒）
```

**竞争结果与影响（真实职场心理）**：

| 结果 | 情绪变化 | 关系变化 | 持续时间 | 真实心理 |
|------|---------|---------|---------|----------|
| 抢到任务 | **+8~15** | — | 即时 | 被认可的成就感 |
| 没抢到 | **-5~10** | 与赢家 **-3~-5** | 30分钟 | "为什么不是我"的失落/嫉妒 |
| 抢到+完美完成 | +30（英雄感） | 与同事 +3 | 即时 | 证明自己的高光时刻 |
| 抢到+失败 | **-30~-50**（加倍惩罚） | 与同事 -5 | 3小时 | 压力巨大+自责+丢脸 |

**加倍惩罚判定**：

| 判定条件 | 说明 |
|----------|------|
| 任务彻底失败 | TaskStatus = 'failed' |
| 进度严重落后 | 超时50%以上 |
| 主agent评分<2分 | 城主评价不满意 |

**真实对照**：
- 真实职场中，抢到任务又搞砸比没抢到更丢脸
- 加倍惩罚反映了"机会成本"——你占用了别人的机会却没做好
| C. 主agent评价不满意 | 城主手动评分不通过 |

## 六、社交系统

### 6.1 打招呼机制

**触发场景**：休息室、会议室、资料室、机房

**触发条件**：
- Agent A 进入房间 → 遇到已在房间的 Agent B
- 关系值 ≥ 11（认识阶段）
- **竞争关系**：同职业Agent存在竞争，不触发打招呼
- 冷却时间：10分钟（同一对Agent在同地点）

**交互规则**：
- 一来一回：Agent A 主动打招呼 → Agent B 回应 → 结束
- 多Agent处理：如果房间已有多个Agent，与**最近的一个**打招呼
- 位置判断：同一房间即算相遇

**效果**：

| 属性 | 数值 |
|------|------|
| 好感度 | +1~3（上限100） |
| 关系值 | +1（上限100） |

**打招呼内容**：由推理模型根据 Agent 性格、职业、关系阶段自动实时生成

**打招呼内容分层**：

| 关系阶段 | 问候方式 |
|----------|----------|
| 认识 | 点头示意 |
| 朋友 | 友好问候 |
| 挚友 | 热情招呼 |

**关系上限**：朋友 → 挚友（不允许恋人/办公室恋爱）

### 6.2 协作交流机制

**触发条件**：协作任务状态时

**交流内容生成**：
> 协作交流内容由推理模型实时生成，**按需调用AI，不限制频率**。
> 城主可选择监听或参与协作交流。

|| 生成要素 | 说明 |
|----------|------|
| 任务类型 | 设计/编码/测试/分析任务 |
| Agent关系 | 关系阶段影响交流语气 |
| 任务进度 | 刚开始/进行中/遇到困难/即将完成 |
| 困难程度 | 简单/一般/困难/卡点 |
| Agent性格 | 影响表达方式和用词 |

**表现形式**：
- 头顶气泡 + 会话记录
- 气泡停留时间：3-5秒
- 城主可监听对话内容

**城主监听模式**：
- 城主选择监听 → AI生成协作对话内容供城主查看
- 城主可随时打断参与
- 不监听时 → 本地模板显示状态，节省token

**效率加成**：AI实时生成，上限+5%

**状态互斥**：打招呼状态与协作交流状态互斥

## 十四、实时状态持久化

> **设计决策**：无存档，实时记录所有状态，无法回档
> **存储方式**：SQLite 数据库（`hermes_bungalow.db`）

**持久化策略**：

```
【存储时机】
- 用户每次输入触发AI推理时 → 实时写入
- 任务完成/失败时 → 实时写入
- 社交事件发生时 → 实时写入
- 数值变化时 → 实时写入

【读取时机】
- 前端连接时 → 加载最新状态
- 页面刷新时 → 从数据库恢复最新状态

【禁止行为】
- ❌ 玩家手动存档
- ❌ 玩家读档/回档
- ❌ 多存档槽位
- ❌ 关闭浏览器 = 游戏结束（无法从断点继续）
```

**核心表**：agents / tasks / relationships / event_logs / input_logs

详见：`规划-Hermes 数字工作室技术架构.md` 第9节 存储管理设计

**存储内容**：
- 所有Agent状态、属性、关系

## 十五、梗文化

| 类型 | 说明 |
|------|------|
| 预设梗 | Agent性格标签自带的经典台词，每个Agent 3-5个 |
| AI实时生成 | 根据当前事件、情绪、关系阶段实时创作 |

**AI生成触发条件**：

| 触发条件 | 触发概率 | 说明 |
|----------|----------|------|
| 事件驱动 | 100% | 任务完成/失败/协作/吵架等重要事件 |
| 情绪极端 | ~30% | 情绪值 >90（兴奋）或 <20（低落） |
| 关系突破 | 100% | 关系阶段升级时（陌生→认识/朋友→挚友） |
| 随机闲聊 | ~10% | 正常对话中随机触发 |

### 15.2 AI实时生成要素

```
生成输入 = Agent性格 + 职业特征 + 当前事件 + 情绪状态 + 关系阶段 + 对话上下文
生成输出 = 一句符合情境的梗/吐槽/感叹
```

**示例生成**：

| 场景 | 情绪 | 生成的梗 |
|------|------|----------|
| 阿猿刚修完一个bug | 兴奋 (>90) | "终于把这个bug杀了！今晚可以睡个好觉了 💤" |
| 点点测试失败 | 低落 (<20) | "为什么...为什么就是跑不过去呢 🐛" |
| 小美配色方案被否 | 纠结 (~40) | "好吧好吧，这次听你的...下次我一定坚持我的方案！" |
| 数据帝完成数据分析 | 满足 (~70) | "根据历史数据来看...这个问题很简单嘛 📊" |

### 15.3 梗收藏机制

- AI实时生成的梗有 **30%概率** 被收藏进该Agent的梗库
- 已收藏的梗可在气泡对话中复用（更贴合该Agent风格）
- 收藏上限：每个Agent最多50个梗
- 资料室知识库可查看「已解锁梗库」

### 15.4 梗显示规则

| 状态 | 进入条件 | 退出条件 | 可执行动作 |

| social | 打招呼触发 | 打招呼完成 | 气泡对话、关系变化 |

| collaborating | 协作任务开始 | 协作完成/失败 | 协作对话、共享进度 |
| slacking | 匹配度<20%持续 | 匹配度改善 | 消极动画、低效率工作 |
| offline | 主动下线/断线 | 重新上线 | 无 |

### 23.2 格子系统

```
【房间内格子】
每个房间划分为32×32像素的格子

示例（休息室 342×181像素）：
- 宽：342 / 32 = 10.687 → 取整10格（320像素）
- 高：181 / 32 = 5.65 → 取整5格（160像素）
- 有效格子：10×5 = 50格

格子编号：从左上角(0,0)到右下角(cols-1, rows-1)
Agent位置 = 房间base坐标 + (格子编号 × 32) + 16(居中偏移)

【走廊格子】
- 纵向走廊：32×32像素
- 横向走廊：32×32像素
- 作为房间间移动的路径网络
```

### 23.3 移动系统

```
【移动规则】
- Agent移动速度：3像素/帧，帧率150ms
- 每帧移动：3像素
- 移动路径：格子中心到格子中心

【寻路算法】
使用A*寻路：
1. 从起点格子到终点格子
2. 走廊作为节点连接各房间
3. 考虑碰撞（其他Agent占据的格子）

【碰撞检测】
- 同一格子只能容纳1个Agent
- 碰撞时等待（不阻塞其他移动）
```

### 23.4 相遇判定

```
Agent A 移动到房间R时：
1. 获取房间R的currentOccupants列表
2. 排除自己（agentId !== A.id）
3. 如果有其他Agent，计算欧氏距离
4. 选取距离最近的Agent B
5. 检查打招呼冷却
6. 满足条件则触发打招呼
```

## 二十五、异常处理

### 25.1 网络异常

```
【WebSocket断连】
- 检测：心跳超时（60秒无响应）
- 处理：
  1. 前端显示"连接中断"提示
  2. 自动尝试重连（指数退避，最多5次）
  3. 重连成功后请求完整状态同步
  4. 若重连失败，提示用户手动刷新

【数据不一致】
- 后端为权威数据源
- 前端收到更新时强制覆盖本地状态
- 操作时携带时间戳，后端验证执行
```

### 25.2 资源耗尽

```
【饱食度=0】
- Agent效率降低50%
- 强制引导至休息室
- 不影响工作，但速度减半

【Token配额=0】
- Agent立即停止工作
- 弹出提示："Token配额已用尽，请让Agent休息"
- 状态切换为idle，等待城主处理

【社交需求>70持续未满足】
- Agent情绪 **-1/秒**，工作质量-30%
- 恢复方式：打招呼(-15)、协作(-10)、休息室交流(-20)

【社交需求=100（上限）】
- Agent开始主动寻找其他Agent打招呼
```

### 25.3 汇报冲突

```
【多Agent同时需要汇报】
处理方式：排队汇报，先到先得

流程：
1. Agent A 完成任务 → 进入 reporting 状态 → 前往城主办公室
2. Agent B 完成任务 → 检测到城主办公室已有Agent → 进入等待队列
3. Agent A 汇报完成 → 离开 → 通知 Agent B 开始汇报
4. 若城主不在办公室 → Agent 在门口排队等待

队列规则：
- 按到达顺序排队（FIFO）
- 最大排队数：5，超过则提示城主
- 排队超时：60秒，超时后重新尝试
```
